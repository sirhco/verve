# 25 — AI tools (`verve.ai`)

`verve.ai` exposes a subset of an app's own typed functions to a language
model as callable tools, then runs the model through a bounded tool-use
loop against them. It is not a chatbot SDK bolted onto Verve — it reuses
the same `Actions` namespace `POST /api/<fn>` already dispatches through
(`docs/03-actions.md`), the same comptime argument reflection, and adds one
new thing on top: an explicit, comptime-checked allowlist that decides what
a model is even allowed to name.

Demo: `/ai-chat` (`zig build run`). Source: `src/app/ai.zig` (the
allowlist), `src/app/api.zig`'s `Actions.aiChat` (the route),
`src/client/islands/AiChat.zig` (the chat UI).

## The allowlist is the security boundary

```zig
// src/app/ai.zig
const verve = @import("verve");

pub const tools: []const verve.ai.ToolDecl = &.{
    .{
        .fn_name = "getCount",
        .description = "Read the current value of the shared counter.",
        .risk = .safe,
    },
    .{
        .fn_name = "addTodo",
        .description = "Append an item to the shared todo list.",
        .risk = .mutating,
        .arg_docs = &.{.{ .field = "text", .description = "Item text, trimmed, max 200 characters." }},
    },
};
```

A function on `app.Actions` is callable by a model **only** if it appears
here. `verve.ai.Registry(Actions, tools)` builds a comptime-validated
dispatch table restricted to exactly this list — a real, exported,
otherwise-public function that isn't in `tools` has no schema, no name a
model can reach, and no code path that dispatches to it. This is
default-deny, not a filter applied after the fact: there is no "expose
everything, then block a few" mode.

Every entry is validated at **compile time**, not first-request time:

- `fn_name` must name a real decl on the `Actions` type — a typo is a
  build failure (`@compileError`), not a runtime 404.
- `arg_docs.field` must name a real field on that function's single struct
  argument — a stale doc entry after a rename is also a build failure.
- The argument type must be representable as JSON Schema
  (`verve.ai.jsonSchema`) — an unsupported type (a raw pointer, a function
  value) is a build failure, not a tool that silently gets an empty
  `input_schema`.

None of this is enforced by convention or code review discipline. It's
enforced by the type checker, the same way a missing struct field is.

## `Risk` tiers

```zig
pub const Risk = enum { safe, mutating, dangerous };
```

- **`.safe`** — reads only, no observable side effects. `getCount`,
  `appName`.
- **`.mutating`** — changes app state (`addTodo`, `removeTodo`). **This is
  the tier's default** (`ToolDecl.risk = .mutating` when unset) —
  deliberately: opting *out* of caution has to be a conscious choice at the
  call site, not something that falls out of forgetting to set a field. If
  you don't say otherwise, a new tool declaration is treated as capable of
  changing state.
- **`.dangerous`** — destructive, irreversible, or outward-facing (sending
  an email, deleting an account, spending money). Never runs without an
  explicit human confirmation round-trip, and — see below — never runs at
  all unless the host's `Policy.allow_risk` opts into it.

The framework never infers a function's risk from what it does. The app
author declares it, and the policy gate enforces exactly what was
declared — the framework does not, for example, try to guess "this
function's name starts with `delete`, better mark it dangerous."

**This demo ships zero `.dangerous` tools.** Shipping one means shipping
the confirmation UI for it too — approving a dangerous action from a
human-facing surface, not just wiring the token plumbing and hoping. A
demo that declares `.dangerous` tools with no way to approve them is worse
than not declaring them: at best they're just refused (see below), at
worst it's a false sense of "we tested this."

## The policy gate

Every tool call — model-issued or desktop-IPC-issued — passes through one
shared gate (`core/ai/registry.zig`'s `gate` function, called by both
`Registry.invoke` and `RouteRegistry.invoke`; see below): **allowlist,
then size, then risk, then confirmation.** Nothing runs until every check
passes, and every outcome — including a refusal — is audited
(`verve.ai.audit`).

```zig
pub const Policy = struct {
    max_steps: u8 = 8,
    max_tool_result_bytes: usize = 16 * 1024,
    allow_risk: Risk = .mutating,
};
```

- **`max_steps`** bounds the whole tool-use loop (`verve.ai.run`), not just
  tool executions — a provider that returns `tool_use` on every single
  call still stops after `max_steps` round trips. This demo sets `6`.
- **`max_tool_result_bytes`** caps what a tool's JSON result can hand back
  to the model. An oversized result is wrapped into
  `{"truncated":true,"partial":"..."}` — a value that still parses, never
  a byte-sliced fragment that could split a string mid-escape or a
  multi-byte UTF-8 codepoint in half.
- **`allow_risk`** is the risk *ceiling* the gate allows, not merely a
  hint. **Its default is `.mutating`** — meaning a `.dangerous` tool
  declared on an app whose `Policy` never raises `allow_risk` is not
  "asked for confirmation," it is **denied outright** with `"risk above
  policy threshold"`, before the confirmation machinery is ever reached.
  Confirmation only exists for a policy that has explicitly opted in via
  `allow_risk = .dangerous`.

## The confirmation round-trip

With `allow_risk = .dangerous`, a `.dangerous` call doesn't execute on
first contact. `gate` mints a confirmation token
(`ToolOutcome.needs_confirmation: u64`) and audits the ask; the tool
result fed back to the *model* is a fixed, token-free string — `"this
tool requires human confirmation; ask the user to approve it"`
(`core/ai/agent.zig`). The token itself has exactly one path out of the
system: to the **caller of `verve.ai.run`** (a host route — this app's
`aiChat` action, or a desktop IPC handler), never through the provider,
never into the conversation the model sees.

To actually redeem one: the host surface a human interacts with (not the
model) presents the pending action, and on approval calls
`Registry.invoke`/`RouteRegistry.invoke` again with that token as
`confirm_token`. `policy.claimToken` checks it against the *exact*
`(tool_name, args_json)` it was minted for — a token issued for `wipe`
cannot authorize `nuke`, and a token that mismatches is audited distinctly
(`.claim_rejected`) from a routine first-time ask (`.needs_confirmation`),
which is what a model trying to spend one tool's approval on a different
call looks like. A claimed token is single-use: replaying it re-asks
rather than re-executing.

This demo does not implement that human-approval UI (see "zero
`.dangerous` tools" above) — the mechanism is exercised by
`core/ai/registry.zig`'s own dispatch tests (`"dispatch: dangerous tool
needs a token, then runs once"` and neighbors).

## Provider selection

`verve.ai.run(arena, provider, Registry, policy, convo, system, model)`
drives the loop against whichever `Provider` the caller hands it — the
loop itself doesn't know or care which one:

- **`verve.ai.anthropic.Client`** — the live Anthropic Messages API.
  `native_tools = true`; it accepts a tool list and returns `tool_use`
  blocks this framework executes. `Client.model` (`"claude-opus-5"` by
  default) and `Client.max_tokens` are the one place those defaults
  live — `provider.Request.model`/`.max_tokens` are `?T = null` precisely
  so a call site never has to restate them. The API key resolves from an
  explicit `Client.api_key` first, then `ANTHROPIC_API_KEY` in the real
  process environment, captured once at server startup
  (`verve.ai.anthropic.initEnviron(init.environ_map)` in
  `src/server/main.zig` — Zig 0.16 has no ambient `getenv`). Neither path
  ever proceeds without a key, and the key is never logged or echoed back
  — a non-2xx response logs only the HTTP status.
- **`verve.ai.MockProvider`** — a scripted, deterministic `Provider` for
  tests and CI. Hands back a fixed sequence of `Response`s, one per
  `complete` call, then `error.MockExhausted`. This demo's
  `mock_turns` (`src/app/api.zig`) script one `tool_use` turn against
  `getCount`, then a final `end_turn` summary.
- **`desktop.ai_cli.Client`** — the Claude Code CLI (`claude -p
  ... --output-format=json`) run as a subprocess, for the desktop target.
  This is **delegation, not tool-calling**: the CLI runs its own tools in
  its own sandbox and never sees this framework's registry.
  `capabilities().native_tools = false`, so `verve.ai.run` refuses up
  front (`error.ProviderLacksToolSupport`) if the caller declared any
  tools at all, rather than silently dropping them. `RouteRegistry` (the
  desktop-IPC sibling of `Registry`, sharing the exact same `gate`/`audit`
  pipeline) exists for an app that wants to wire a tool-calling desktop
  route the same way `Registry` wires an HTTP one; this demo doesn't ship
  one.

### `VERVE_AI_MOCK`

`Actions.aiChat` picks `MockProvider` over a live `anthropic.Client` when
`VERVE_AI_MOCK` is present in the environment `src/app/ai.zig`'s
`initEnviron` captured at startup — the same environment-capture pattern
`anthropic.initEnviron` uses, wired next to it in `src/server/main.zig`.
This is what lets `tests/integration.zig` exercise `POST /api/aiChat` with
**no `ANTHROPIC_API_KEY` and no network call**: the spawned test server's
environment carries `VERVE_AI_MOCK=1`, and every turn plays out against
the scripted transcript instead of a live request.

```sh
VERVE_AI_MOCK=1 zig build run
# POST /api/aiChat now answers from mock_turns, not the network.
```

## The `/ai-chat` demo

`Actions.aiChat(args: struct { prompt: []const u8 }) ![]const u8` runs one
full agent turn (synchronous on the request thread — non-streaming,
bounded by `Policy.max_steps`; a streaming version needs the push hub from
`docs/06-realtime.md` and is a later cluster) and returns the model's
final text.

The reply is written into a **threadlocal fixed buffer**
(`tl_ai_reply`), not heap-allocated and returned from `page_allocator` —
the api_handler serializes an action's return value on the same request
thread immediately after the action returns (see `vizGraph`'s
`tl_nodes`/`tl_edges` in the same file for the established pattern), so
there's no cross-thread race and, critically, nothing that would ever
free a `page_allocator.dupe`'d string. A reply longer than the buffer is
truncated **explicitly**, at a UTF-8-safe boundary, with a visible
`" [truncated]"` marker — never silently.

The client island (`src/client/islands/AiChat.zig`) does **not** receive
the transcript as island props. Island props are capped at 8192 bytes
(`island_scratch` in `src/client/runtime_exports.zig`), and a multi-turn
transcript will exceed that. Instead the chunk keeps its own bounded
message history and re-renders it after each server-fn round trip —
`verve.serverFnPostRid` + `verve.registerResponseHandlerOnce` +
`verve.parseJson`, the same request/typed-reply pattern
`JsonProbe.zig`/`WsDemo.zig` already use (`docs/20-client-runtime.md`).

## Security model

State this plainly, because it's the part that matters most:

- **The comptime allowlist (`Registry`/`RouteRegistry`'s `decls`) is the
  entire security boundary.** A function is reachable by a model if and
  only if it is named in a `[]const ToolDecl` passed to `Registry` or
  `RouteRegistry`. There is no other gate, no runtime permission check
  layered on top that a misconfigured allowlist could fall back on.
  Whatever is in the list is what's exposed — full stop.
- **Deciding a function is safe to expose, and at what `Risk`, is the app
  author's job. The framework does not and cannot make that call for
  you.** It cannot infer that `deleteAccount` is dangerous from its name,
  that `addTodo` is safe to let a model call unattended, or that a
  function with no side effects today will still have none after the next
  refactor. Every `ToolDecl` in `tools` is a claim the app author is
  making, checked by nothing but their own judgment at the point they
  wrote it.
- **The desktop JS shim is not a trust boundary.** `verve_desktop.js` and
  the webview's `window.verve.request(...)` surface are a transport, the
  same way `fetch` to `/api/<name>` is a transport on the web target.
  Nothing about running behind a native window changes what's safe to
  expose — a function that shouldn't be a model tool over HTTP shouldn't
  be a model tool over desktop IPC either, and `RouteRegistry` enforces
  the identical gate for exactly that reason (see "Provider selection"
  above). Don't reach for `.dangerous` risk classification, or skip the
  allowlist, on the theory that the desktop build is somehow more
  trusted.
- **No API key reaches the browser, a log line, or a response body.** The
  Anthropic key resolves server-side only (`anthropic.resolveApiKey`),
  is never serialized into any `Response`, and a failed request logs only
  the HTTP status code (`std.log.scoped(.verve_ai).err("anthropic: http
  {d}", .{res.status})`) — never the response body, which could echo
  request content back verbatim.
- **A confirmation token authorizes one exact `(tool, args)` pair, once.**
  It is minted for a human-facing approval UI, never handed to the model,
  and single-use once claimed (see "The confirmation round-trip" above).
  A model cannot phish a user into approving a different action than the
  one actually pending — the token binding is checked server-side, not
  trusted from whatever the client claims it's approving.
- **A `.dangerous` tool with no `Policy.allow_risk = .dangerous` anywhere
  in the host is not "pending confirmation" — it is unconditionally
  denied.** The default `Policy.allow_risk` is `.mutating`; raising the
  ceiling is an explicit, auditable choice a host has to make, not
  something that happens by declaring a tool `.dangerous` and moving on.
